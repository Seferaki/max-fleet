# Передача backend между двумя ноутбуками

Цель: новый аккаунт Codex продолжает по репозиторию, не восстанавливая историю чужого чата. Один активный backend-исполнитель; data engineer и QA работают в своих ветках. Автоматического переноса локальных файлов/секретов/volumes между аккаунтами нет.

## 1. Что является источником прогресса

| Источник | Содержание |
|---|---|
| IMPLEMENTATION_PLAN.md | Зависимости и критерии задач |
| progress/BACKEND.md | Очередь ноутбуков, выбранная задача, checkpoint и следующий шаг |
| progress/DATA.md | Прогресс только data engineer и gate готовности Python |
| progress/QA.md | Проверки и дефекты, различение mock и real |
| Git commits / CI | Реальное доказательство кода и проверок |

Не доверять отметке DONE, если commit отсутствует в доступной удалённой ветке. Текст чата — пояснение; восстановимый код и текущий статус должны быть в Git.

Файлы статуса имеют YAML-блок и таблицу задач. YAML содержит только не-секретные значения. `last_verified_code_commit` — SHA **предыдущего коммита с проверенным кодом**; его не подменяют SHA коммита статуса. Так нет задачи записать hash коммита внутрь самого себя.

## 2. Ветки и первый старт

После добавления документации в общую main:

1. Первый backend создаёт `codex/backend` от актуальной main. Оба ноутбука последовательно работают с **этой же удалённой веткой**, не со своими расходящимися копиями.
2. S-02 публикует общий контракт в общей базе, затем data engineer начинает `codex/data`, QA — `codex/qa`. Если ветки существовали раньше, они получают один и тот же contract commit.
3. Изменения в backend до INT идут только в codex/backend. В своей ветке DE не редактирует progress/BACKEND.md.
4. INT создаёт codex/integration от готового backend и сливает data/QA. Backend lock продолжает применяться к интеграционной ветке.
5. Защищённая main не обходится. Если требуются PR, агент готовит их и запрашивает лишь недостающее право/обязательное решение владельца.

Целевой запуск на новом ноутбуке (агент выполняет команды; путь/ветку берёт из актуального статуса):

```text
git clone https://github.com/Seferaki/max-fleet.git
cd max-fleet
git fetch origin
git switch --track origin/codex/backend
git pull --ff-only
git status --short
```

При первом создании ветки — git switch -c codex/backend origin/main; при уже существующей локальной — git switch codex/backend. Не выполнять слепо switch --track второй раз. При dirty tree сначала выяснить происхождение изменений; ничего не стирать и не делать reset --hard. Незакоммиченные файлы другого ноутбука этой командой не появятся.

## 3. Захват очереди — перед любой реализацией

В progress/BACKEND.md хранится: lock_state (FREE/ACTIVE/HANDOFF/INTERRUPTED), owner (A/B/не назначен), session_id (новый UUID), branch, heartbeat_utc, current_task и current_substep.

1. Fetch/pull --ff-only; убедиться, что локальная ветка равна remote и worktree чист.
2. Если FREE или HANDOFF — подготовить отдельный claim-коммит: ACTIVE, свой owner/session, время и выбранная задача. Сначала commit/push, **после успешного push** менять код.
3. Обычный push работает как compare-and-swap remote HEAD: если оба ноутбука начали с одной базы, один получит non-fast-forward. Проигравший не rebase-ит claim поверх чужого ACTIVE; перечитывает статус и прекращает backend-работу.
4. ACTIVE у другого ноутбука не означает, что можно забрать очередь по таймеру. Старый heartbeat — повод проверить, не остался ли выполняющийся агент/процесс.
5. Чтобы забрать ACTIVE после исчерпания лимита, человек должен явно сообщить, что прежний исполнитель остановлен, либо прежний ноутбук публикует HANDOFF. Это предотвращает два параллельных владельца. В записи отметить takeover и причину.
6. Перед каждым code push снова fetch и сверить session_id/owner. Если remote изменился чужим claim — остановить запись в общую ветку, сохранить свою работу в отдельной recovery-ветке и разобрать различия.
7. Refresh heartbeat вместе с каждым checkpoint. Lock — организационный протокол с Git-конфликтом, не распределённая блокировка процесса.

Этот единственный короткий вопрос при аварийном takeover нужен именно для предотвращения потери чужой работы. Если очередь свободна, повторное человеческое разрешение не требуется.

## 4. Рабочий цикл агента

- Выбрать ближайшую TODO с выполненными зависимостями. Прочитать только относящиеся к ней требования.
- Разбить задачу на шаги примерно по 15–30 минут или один проверяемый результат. Не планировать большой незакоммиченный блок до предполагаемого окончания лимитов.
- Перед изменением записать current_substep и next_step. После изменения — релевантная проверка и обычный code commit с ID задачи.
- Проверить staged diff/secret scan. Коммитить явно выбранные пути; не добавлять вслепую все untracked файлы.
- Затем отдельный status commit: SHA проверенного кода, команды/результаты, remaining, next_step; push обоих.
- Если проверка красная, можно опубликовать checkpoint в рабочую ветку с `checkpoint_state: WIP`, точной ошибкой и `DONE` не ставить. Такой commit не release и не должен попадать в main без исправления.
- После каждого meaningful checkpoint обновить человеческое сообщение: что сделано, что проверено, что дальше.

Пример названий: `feat(BE-05): validate and replace inspection photo`, `docs(BE-05): checkpoint and next step`. Проверки/логи с личными данными или секретами не коммитить.

## 5. Плановая передача ноутбуку B (и обратно)

1. Завершить маленький подшаг; остановить обработчики реального MAX на этом ноутбуке, если новый будет использовать тот же token. Сервер с общим webhook не выключать ради переключения разработки.
2. Сохранить код и соответствующий проверенный commit; проверить, что push успешен.
3. В статусе: lock_state=HANDOFF, checkpoint_state=VERIFIED/WIP, owner=текущий, current_task, last_verified_code_commit, next_step, точные команды и оставшиеся ошибки.
4. Перечислить только **имена** нужных секретов и их местонахождение (например локальный secrets/max_bot_token), не значения.
5. Отдельно указать state данных: synthetic seed достаточен / нужен приватный backup / dev consumer остановлен. Обычно второй ноутбук начинает с синтетических данных; Git не переносит БД.
6. Commit/push статуса. Сравнить remote SHA с локальным через git ls-remote; при отсутствии сети не говорить «передано».
7. На втором ноутбуке открыть репозиторий, запустить prompts/BACKEND.md; агент перечитает состояние, claim-ит очередь и продолжит.

Пользователь делает минимум: открывает нужный репозиторий на другом ноутбуке и запускает один промпт. Аккаунты GitHub могут быть разными, но оба должны иметь write-доступ. Секреты один раз вводятся локально либо передаются через согласованный приватный менеджер паролей.

## 6. Внезапно закончился лимит или пропало питание

| Состояние | Действие следующего исполнителя |
|---|---|
| Есть свежий pushed checkpoint | Проверить остановку прежнего владельца, takeover; выполнить next_step |
| Код запушен, status остался старым | Сравнить git log/diff после recorded SHA, запустить относящиеся проверки, восстановить статус по фактам |
| Code commit только локальный | На первом ноутбуке вручную push обычным Git; второй до этого может продолжить лишь от последнего remote checkpoint |
| Есть uncommitted edits | На первом ноутбуке сохранить WIP-коммит после проверки секретов и push; не пересылать весь каталог с .env/volumes |
| Первый ноутбук недоступен | Честно считать непереданные изменения недоступными; продолжать от последнего remote состояния после takeover |
| Прерван merge/rebase | Прочитать git status, не повторять операции вслепую; сохранить конфликтующие изменения, закончить merge по смыслу |
| Push отклонён | Fetch, проверить владельца; не force push. Если владелец тот же и нет чужого claim, разрешить конфликт небольшим merge |
| Лимит закончился раньше checkpoint | Память чата это не компенсирует; поэтому checkpoint делается регулярно заранее |

Невозможно гарантировать перенос байтов, которые никуда не были сохранены. План снижает потери частыми commit/push, но не обещает чудесного продолжения из неопубликованного локального состояния.

## 7. Пример полноценного checkpoint

```yaml
lock_state: HANDOFF
owner: A
session_id: "example-session"
branch: codex/backend
current_task: BE-05
current_substep: "Проверена замена одного ракурса"
last_verified_code_commit: "<реальный полный SHA из git rev-parse HEAD>"
checkpoint_state: VERIFIED
contract_commit: "<проверенный SHA S-02>"
next_step: "Добавить отказ для сообщения с несколькими изображениями; затем тест дубля event"
human_required: []
```

Рядом текстом: изменённые пути; команды с exit status; какие тесты не выполнялись; известные ошибки; нужно ли поднять mock/full; важное решение с ссылкой. Секреты и реальные пользовательские ID исключены.
