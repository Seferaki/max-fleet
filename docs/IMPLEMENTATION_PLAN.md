# План реализации MAX Fleet

Версия 1.0, 26.09.2026. Цель: рабочий P0 из [PRODUCT_SPEC](../PRODUCT_SPEC.md) в Docker, Go и Python разрабатываются независимо, реальное соединение выполняется **последним этапом INT**. Текущий запрос создал план, не реализацию.

## 1. Как читать и исполнять

- Backend: [прогресс](progress/BACKEND.md) → [передача ноутбуков](HANDOFF.md) → задача ниже → [промпт](../prompts/BACKEND.md).
- Data engineer: [прогресс](progress/DATA.md) → [задание](DATA_ENGINEER.md) → [таблицы](DATABASE.md) → [контракт](API_CONTRACT.md).
- QA: [прогресс](progress/QA.md) → [один файл требований](QA_REQUIREMENTS.md).
- Статус задачи хранится только в файле своего направления; этот план хранит зависимости и Definition of Done. Не ставить здесь параллельные галочки, которые расходятся с реальным прогрессом.
- Статусы: TODO, IN_PROGRESS, BLOCKED, DONE. BLOCKED содержит конкретный внешний блокер, затронутые задачи и независимый следующий шаг. Не путать ожидающий тест с пройденным.
- Перед задачей записать ID, подшаг, owner, ветку и commit базы. После проверяемого подшага — checkpoint. Детали — HANDOFF.
- Готовность: код/документы + релевантные проверки + запись результата/commit + push. «Похоже работает» и скрин mock не закрывают интеграцию.

## 2. Роли и границы файлов

|---|---|---|

| Data engineer | services/data/, deploy/compose.data.yaml, data CI, progress/DATA.md, DATABASE уточнения | MAX token, Go-код, чат второго аккаунта |

| Исполнитель S-02 | contracts/, согласованные DTO/errors/fixtures | Изменения доменных правил без фиксации причины |

Общие .env.example, scripts и root CI создаёт backend; data engineer вносит своё расширение через отдельный PR/коммит по задаче, без случайной перезаписи. Схему/контракт не меняют одновременно в двух ветках. Изменение записывается, обе ветки получают один и тот же commit.

## 3. Этапы и ориентир времени

| Этап | Содержание | Gate |
|---|---|---|
| Старт | S-01…S-03: доступы, договорённости, контракт, каркасы | Один зафиксированный контракт и fixtures доступны обоим трекам |
| Backend независимо | BE-01…BE-12 + UI-01 | Все P0 Go/UI сценарии и сбои проходят с mock; mode явно mock |
| Data независимо | DE-01…DE-09 | Миграции, API, S3, гонки, нагрузка и восстановление проходят отдельно |
| QA параллельно | QA-01…QA-03 | Требования преобразованы в проверки; результаты привязаны к конкретному режиму |
| Финал | INT-01…INT-06 | Go → Python → PostgreSQL/S3, затем реальный MAX, QA и восстановление |

Ориентир хакатона: день 1 — контракт и минимальные отдельные контуры; день 2 — взятие/возврат/данные; день 3 — админка/надёжность/независимая приёмка; день 4 — весь INT. Это оценка, не гарантия: 8+8 фото, административные сценарии и реальная модерация делают срок напряжённым. При нехватке времени честно показать невыполненные P0; не переводить их в DONE или незаметно в P1. Адрес по координатам, экспорт и создание машины ботом остаются P1. К P1 после приёмки P0 также относится вывод автомобиля из эксплуатации (`retired_at`): он должен убрать машину из доступности, сохранив историю поездок и замечаний.

### Решения по review data engineer для MVP (30.09.2026)

- Блокирующая ошибка одометра устранена: администратор может с CAS и аудитом скорректировать только snapshot машины во время активной брони/поездки; история назначения, осмотр и 8 фото остаются неизменными. Рост показания больше 1000 км просит подтверждение у сотрудника; произвольный верхний предел не вводится.
- Замечания имеют исполнителя `assigned_to`; доступны отдельные категории `parking`, `car_lock`, `post_return`. Вопрос возврата про закрытие машины и ключи остаётся одним составным шагом интерфейса; контракт хранит `car_locked` и `keys_returned` отдельными проверяемыми значениями.
- 8+8 фото и 15-минутный hold сохраняются. Продление hold до 20–25 минут не вводить без решения владельца бизнес-правила.
- Контактные данные не добавлять до приватного seed/решения H-03. Срок хранения персональных данных и фото, доступы и политика backup нужны для пилота по H-04; до решения используются только синтетические данные. Вывод машины из эксплуатации (`retired_at`) остаётся P1 после P0.
- 30.09.2026 по запросу владельца подготовлен русский policy pack для demo и будущего пилота: правила поездки, данные/доступ/предлагаемые сроки хранения, backup/recovery и incident response. Для synthetic demo он задаёт рабочее поведение; для настоящих данных сроки и контроли остаются предложением до проверки и утверждения оператором. Автоматическая очистка по срокам не реализована; наличие документов не доказывает настроенное retention или расписание backup.
- Сверка контрактных вопросов и DE smoke фиксируется в `progress/DATA.md`; готовность Python не подменяет отдельную проверку Go → Python и не закрывает QA. QA может быть пропущена по прямому решению владельца, но результат остаётся `NOT RUN`, а не `PASS`.

## 4. Общая подготовка — backend начинает, DE и QA читают

### S-01 — исходные данные, организационные действия, очередь

Зависимости: нет. Исполнитель: backend A либо B, который начал первым.

1. Проверить remote, ветку, права push и текущий прогресс; создать ветки по HANDOFF. Не работать двум ноутбукам в backend одновременно.
2. Подтвердить архитектуру ADR-01/02, отметить рабочие defaults ADR-07…10. Изменения бизнес-правил записать отдельно.
3. Выполнить доступную автоматически диагностику Git/Docker; выяснить состояние H-01…H-04 из OPERATIONS. Запросить только действия, требующие аккаунта/решения владельца.
4. Подготовить синтетические 10 машин и тестовых сотрудников; реальный seed оставить приватным.
5. Дать человеку короткую инструкцию создания MAX-бота и запуска модерации сразу; ожидание не блокирует mock/DE.
6. Убедиться, что .gitignore закрывает секреты, volumes и дампы; staged diff не содержит настоящих данных.

Артефакт: заполненные поля готовности доступов и owner в progress/BACKEND.md; список HUMAN_REQUIRED без значений секретов. Готово: второй ноутбук видит запись по Git, обе роли понимают next task. Human gate H-01 не обязан быть завершён для DONE этой подготовительной задачи: требуется корректно оформленный запрос и независимый путь продолжения.

### S-02 — заморозить контракт до параллельной реализации

Зависимости: S-01. Исполнитель: backend; data engineer проверяет границы и может дать замечания.

1. Прочитать API_CONTRACT и DATABASE. Оформить OpenAPI, enums, DTO, обязательные поля и error codes; не добавлять прямой SQL в Go.
2. Определить version bump для aggregate/inspection/conversation; порядок блокировок, scope идемпотентности и event keys MAX.
3. Прописать все команды/очереди/фото/чтения, указанные в контракте, включая previous-inspection projection и current-state recovery.
4. Создать синтетические JSON examples и тестовый сценарный набор из раздела fixtures; часы/UUID в mock управляемые.
5. Уточнить ограничения фото, текста, auth_date; pin версию MAX SDK, проверить реальные типы message/callback/photo/geo по документации.
6. Проверить OpenAPI linter, валидность каждого fixture и непротиворечивость маршрутов; записать hash/commit v1.
7. Опубликовать контракт в общей базе обеих веток до их разделения. Если сервисы уже начались, синхронизировать тот же commit.

Артефакты: contracts/data-api.openapi.yaml, contracts/examples/, contracts/scenarios/, короткий contracts/CHANGELOG.md. Готово: mock и Python могут независимо реализовать весь API без устных договорённостей; список schema errors проверен. Изменения контракта после gate — отдельный совместимый commit с причиной.

### S-03 — воспроизводимый каркас и проверки

Зависимости: S-02. Исполнитель: backend; DE использует контракт и начинает DE-01.

1. Создать целевые каталоги без фиктивной бизнес-реализации; Go module, React/Vite package и lock files.
2. Зафиксировать версии toolchain/images; Dockerfile каждого создаваемого сервиса с non-root runtime и healthcheck.
3. Добавить безопасный .env.example только с пустыми secret-полями, scripts/bootstrap.ps1 и .sh: генерация локальных service/storage секретов без вывода.
4. scripts/verify.ps1 и .sh принимают направление; умеют объяснить отсутствующий Docker и не притворяются успешными.
5. CI отдельно валидирует контракт, Go, frontend и позже data. Подключить secret scan staged/CI без отправки содержимого секретов внешним сервисам.
6. Собрать каркас на чистом checkout. Пока сервиса нет, health не выдаёт ложное ready.

Артефакт: структуры, lock files, Dockerfile, базовый CI, воспроизводимые команды. Готово: чистая сборка каркаса; README команды помечены фактическим статусом.

## 5. Backend Go — выполняется последовательно ноутбуками A/B

### BE-01 — HTTP-клиент данных и управляемый mock

Зависимости: S-03.

1. Сгенерировать/описать типизированный DataAPI client по OpenAPI; конфиг DATA_API_BASE_URL.
2. Создать отдельный cmd/data-mock с теми же HTTP-маршрутами, версиями, ошибками и auth-header проверками.
3. Реализовать fixtures пользователей/машин и последовательные сценарии; внедрить fake clock, сценарии timeout/409/503.
4. Для возобновления mock использовать атомарный файловый snapshot в отдельном named volume; только один экземпляр. Не делать mock доказательством production-транзакций.
5. Добавить mode=mock в meta/diagnostics и жёсткий запрет mock в production.
6. Проверить контрактные сценарии и восстановление mock после перезапуска.

Готово: один Go client работает против mock без знания его внутреннего состояния; fixture «неизвестный пользователь» и failed save проверены. Артефакты: dataapi client, mock, deploy/compose.backend.yaml.

### BE-02 — адаптер MAX и надёжный вход событий

Зависимости: BE-01; реальный токен необязателен.

1. Обернуть официальный MAX Go SDK интерфейсом transport; тестовый transport записывает исходящие сообщения.
2. Поддержать bot_started, message_created, message_callback, одно фото и geo; проверить имена по pinned SDK.
3. Webhook: secret header, лимит тела, schema validation, durable inbox перед HTTP 200; обработка в worker.
4. Polling только dev: single-poller lease, durable marker после записи пачки; одновременно webhook и polling запрещены.
5. Очередь по actor, worker leases, backoff, dead state, graceful shutdown; неизвестные события безопасно отклоняются/игнорируются с метрикой.
6. Проверить duplicate event, DB/mock down, restart после приёма, неверный secret, групповое сообщение.

Готово: потеря процесса не создаёт лишний доменный переход; принятые события доступны после restart. Реальный smoke на MAX отмечать отдельно, не блокировать следующий mock этап ожиданием H-01.

### BE-03 — доступ, меню и карточки

Зависимости: BE-02. Покрытие: AC-01, AC-02, AC-04.

1. /start и /menu получают /me и /state; неизвестному показывается только ID.
2. Меню зависит от роли и незавершённого потока, не сбрасывает прогресс.
3. Список по 5, обновление, пустой список, старая кнопка; карта/ключи/даты в карточке.
4. Отдельная обезличенная previous-inspection проекция; не показывать чужого водителя.
5. Сценарии blocked driver и admin без права поездки.

Готово: golden/snapshot проверки текста и кнопок, ACL и пагинация; карточка без места/ключей недоступна к выдаче.

### BE-04 — оформление, math и правила

Зависимости: BE-03. Покрытие: AC-03, AC-05, AC-11.

1. Намерение само не начинает trip; подтверждение создаёт hold и показывает срок.
2. Math: четыре ответа, неверный ответ, третья ошибка, TTL, stale callback, actor mismatch.
3. Версия правил и явное принятие; подтверждение отмены; истечение hold.
4. Восстановление шага по API, отсутствие локальной production state machine вместо Python.

Готово: mock сценарии take/cancel/expired/conflict; второе нажатие не создаёт вторую попытку.

### BE-05 — загрузка, замена и просмотр фото

Зависимости: BE-04. Покрытие: AC-06…AC-08.

1. Последовательно запрашивать 8 заданных ракурсов, по одному изображению.
2. Пересылать поток Python/mock; ограничить тип, размер, время и доверенные источники скачивания.
3. Счётчик менять только после ready; поддержать 7/8, девятое, видео/документ, multi-image, дубль event/hash.
4. Выбор замены конкретного slot, сброс подтверждения комплекта, остальные 7 не меняются.
5. Просмотр before/after и ошибки недоступного объекта с разрешёнными правами.

Готово: тесты каждого отказа и прерванной загрузки; secret/URL/bytes не печатаются в логах.

### BE-06 — данные осмотра, проблема до выезда, начало

Зависимости: BE-05. Покрытие: AC-09, AC-10, AC-26.

1. Уровни топлива, одометр с проверкой формата/отрицательного/меньшего значения.
2. Новое замечание: категория, описание, до 3 stage-фото, сводка, submit.
3. При issue-before показать отмену оформления/блок машины только после сохранения.
4. Итоговая сводка, attestation, start с тем же ключом при повторе; карточка active trip.
5. Потерянный ответ после commit: запросить состояние/результат, не говорить «не началась» без проверки.

Готово: полный take на mock и все ошибки; уведомление создаётся из доменного события, не до сохранения.

### BE-07 — активная поездка и возврат

Зависимости: BE-06. Покрытие: AC-16…AC-20, AC-25.

1. Текущая поездка, проблема во время, контакт ответственного.
2. Намерение return, math, checklist, топливо/одометр и after-фото.
3. Повреждение/грязь разрешают завершение с запретом выдачи; проблемы ключей/закрытия/парковки ведут к администратору.
4. Геопозиция MAX всегда требует подтверждения; альтернативная карта доступна сразу.
5. Отмена возврата возвращает active trip; новый return ID не наследует фото/точку.
6. Финальная сводка/complete; pending при сбое, только подтверждённый успех освобождает машину.

Готово: полный return на mock; AC-18 и fresh draft после cancel проверены. Карта подключается в UI-01.

### UI-01 — обязательный экран карты

Зависимости: BE-07; допускается разработка после BE-01 при готовом контракте.

1. React/TS/Vite + MAX UI/Bridge; Leaflet с настраиваемыми тайлами/атрибуцией.
2. Стартовый центр — последняя парковка/город, selected=false; клик/drag включает подтверждение.
3. Без разрешения GPS ручной выбор работает; ориентир необязателен.
4. Go endpoint валидирует raw initData, auth_date, actor/return/version; не доверяет initDataUnsafe.
5. Ошибка тайлов, запрет geo, timeout submit, reopen с новым/старым return; выбранную точку сохранять при retry.
6. Vitest/Playwright или эквивалент: неподтверждённый центр, чужой return, поддельная подпись, отсутствие разрешения.

Готово: карта и Go endpoint проходят на mock; реальный Bridge на мобильном и web MAX остаётся INT-04. Отсутствие отдельного frontend-разработчика не снимает эту P0-задачу: владелец — backend.

### BE-08 — история и замечания

Зависимости: BE-07, UI-01. Покрытие: AC-21 и сценарии истории.

1. Свои trips по 5, детали/фото/замечания, пометки admin close.
2. Отменённые checkout не смешивать с trips; immutable завершённая история.
3. Сообщение после возврата из карточки; не обвинять последнего водителя автоматически.
4. Тестировать IDOR через подменённые кнопки, ID, курсор и asset.
5. Для собственной завершённой поездки сохранять `issue_post_return` как отдельный разговор: категория, описание, до 3 фото, просмотр и идемпотентная отправка `issue.create` с `trip_id` и `inspection_id=null`. Не менять завершённый Trip и осмотр; отказать чужому/устаревшему ID; восстановить отправку после потери ответа.
6. Добавить категории замечаний `parking` и `car_lock`; OpenAPI, примеры, mock и Python должны получить один contract commit до INT.
7. Из карточки «Предыдущий осмотр» дать сотруднику открыть фото по ракурсу из последнего finalized after; API принимает только ID машины/слота, проверяет доступ, не раскрывает trip/driver/asset ID, проверяет ошибки хранилища и restart.

Готово: разрешённые данные видны, чужие защищены; пустая история объяснена.

### BE-09 — администратор и аварийные операции

Зависимости: BE-08. Покрытие: AC-22, AC-23, AC-25.

1. Dashboard, активные trips, фильтры по машине/сотруднику, просмотр before/after.
2. Выдача/отзыв доступа сотрудника, блок/разблок машины: причина, сводка, math.
3. Изменить описание/ключи; исправить snapshot свободной машины; активной добавить отдельное уточнение.
4. Исправить тупик ODOMETER_ROLLBACK: при active hold/trip admin может аудируемо скорректировать только odometer snapshot с причиной и CAS vehicle.version; определить единственное активное назначение, не менять его и исходный inspection/8 фото. MAX-диалог сохраняет введённое неотрицательное значение и причину до явного подтверждения, показывает старое/новое значение и проверяет admin actor и версию; math challenge для этой операции контрактом не требуется. В BE-06 уже есть повторный запрос подтверждения у сотрудника при приросте более 1000 км за поездку; не подменять его произвольным верхним пределом. Для возврата оба сравнения (inspection.update и return.complete) используют текущий подтверждённый snapshot, который до отдельной коррекции равен пробегу выезда. Проверить права, stale version, ошибки фото, retry/restart после потерянного ответа и гонки correction/start/complete.
5. Разбор issue: админский MAX-список/карточка и переходы in_progress/resolved/known_nonblocking с назначенным администратором (`assigned_to`). При `open → in_progress` назначить ID только из проверенного admin actor, сохранить при закрытии; достаточно статуса, комментарий и подтверждение не требуются. Терминальные решения требуют непустого комментария и подтверждения. Черновик комментария и ожидаемый `issue.version` переживают restart; actor, CAS и idempotency обязательны. Клиент не может указать чужого назначенного. Нельзя unblock при открытой/in_progress blocking issue.
6. Admin close: причина, доступные сведения, missing_data, math; авто needs_review и уведомление водителю. MAX сохраняет trip ID/version, причину, только явно известные поля и состояние challenge до доменной команды; после restart продолжается тот же intent. Неизвестные фото, ключи, координаты и прочие сведения не подменять нулями/false.
7. Невозможность назначить себе admin, старые proof, неверный actor, повтор.
8. Контакты сотрудника/ответственного добавлять только после определения владельца, доступа и срока хранения; UI не должен показывать отсутствующий контакт.
9. В challenge для block/unblock/grant/access/admin_close проверять operation-specific payload без лишних ключей; итоговая команда обязана совпасть с intent SHA-256 и поглотить challenge proof один раз. Для grant target_id и expected_version равны null. Для admin close hash включает все передаваемые `available_data`; Python и mock обязаны отвергнуть подмену после подтверждения.
10. До хранения контактов и других персональных данных определить владельца данных, круг доступа, цели использования, сроки хранения/удаления и поведение резервных копий; пока политика не согласована, не показывать отсутствующие контакты и не расширять реальный сбор данных.
11. Hold остаётся 15 минут по текущему требованию. Предложение увеличить время до 20–25 минут оценивать по замерам завершения оформления/сети; не менять контракт и timeout до продуктового решения.

Готово: все админские действия/отказы на mock; UI показывает последствия до commit.

Проверка возврата: один вопрос «Машина закрыта, ключи возвращены по правилам?» предлагает четыре комбинации, чтобы сохранить keys_returned и car_locked раздельно и честно одним inspection.update. При приросте одометра строго свыше 1000 км за поездку повторно показать значение и запросить подтверждение перед сохранением; границу нужно сопоставить с реальными поездками до интеграционной приёмки. Если значение ниже из-за ошибочного snapshot, коррекция активного автомобиля меняет только одометр snapshot и аудит; immutable inspection, все 8 фото и assignment остаются прежними.

### BE-10 — уведомления и восстановление

Зависимости: BE-09. Покрытие: AC-12, AC-20, AC-24.

1. Claim/ack/retry delivery через отдельный WorkerBearer; стабильные ключи переходов привязаны к delivery и текущему lease. Для временных ошибок — exponential backoff; ошибку лимита MAX повторять, после 5 попыток переводить delivery в dead. Невалидный адресат и неподдерживаемый event сразу dead-letter.
2. Уведомления начала/возврата/issue/блокировок/admin close/access grant/change только из outbox: все администраторы получают событие; при admin close дополнительно уведомляется водитель, при выдаче или изменении доступа — затронутый сотрудник.
3. После restart worker продолжает pending/retry из data service; /menu восстанавливает flow по API.
4. Проверить падение после domain commit и после MAX send до ack; при неопределённом результате MAX повтор может дать дубль, поэтому фиксировать только гарантию at-least-once.
5. Логи request_id/operation/error_code; метрики возраста старшей записи очереди по enqueued_at, retries/dead/ошибок, без actor ID, текста причины, PII или secret.

Готово: воспроизводимые fault-сценарии с mock transport; trip не откатывается при ошибке уведомления.

## 9. Общий Definition of Done

Для любой задачи: указан ответственный и commit → артефакт существует → проверка воспроизводима → результаты честны → no secrets/PII → status/next_step обновлены → push подтверждён. Для changed contract/schema обновлены docs, fixtures и миграции. Для UI проверены реальные сообщения/ошибки; для транзакций — PostgreSQL, не SQLite.

Команды создаются вместе с кодом. Целевой набор: go test/race/vet; Python pytest/ruff/type check; npm typecheck/test/build; OpenAPI validation; docker compose config --quiet, build, up --wait и smoke. Не выдавать отсутствующие пока scripts за работающие.

При неожиданном сценарии сначала сохранить данные/текущий статус и воспроизведение; найти нарушенный FR/BR. Если поведение не определено — записать краткое решение и уточнить у владельца, продолжая независимую задачу. Не менять восемь фото, роли, атомарность или обязательный ручной выбор карты ради прохождения теста.
