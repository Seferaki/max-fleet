# Требования к продукту и задание QA

Версия 1.0, 26.09.2026. Это основной файл QA: требования, проверяемые результаты и рекомендации. Детальные тексты экранов — [PRODUCT_SPEC](../PRODUCT_SPEC.md). Все требования ниже относятся к P0, если не указано иное. **Проверки ещё не выполнены.**

## 1. Продукт и правила проверки

Одна компания, примерно 10 машин, роли employee/admin. Основной интерфейс — личный чат MAX; ручной выбор парковки — React mini-app. Go обслуживает интерфейс, Python владеет данными и правилами. До финального INT используется mock; успешный тест mock подтверждает только этот режим.

Рабочие значения: hold 15 минут; math 5 минут, 4 ответа, новый после 3 ошибок; 8 фото before + 8 after; топливо 0/25/50/75/100; история/списки по 5. Счёт времени серверный. Эти значения фиксируются в контракте и не меняются для упрощения тестов.

## 2. Функциональные требования

| ID | Требование / действие | Проверяемый результат |
|---|---|---|
| FR-01 | Неизвестный пользователь открывает бота | Видит только инструкцию и свой MAX ID; машина/история/админка недоступны |
| FR-02 | Роль и запрет доступа | Сотрудник не получает admin через payload; blocked не начинает новую поездку, но возвращает свою active и сообщает о проблеме |
| FR-03 | /start, /menu, назад, повторный вход | Не отменяют trip/hold/return, следующий шаг восстанавливается; отмена — отдельное подтверждённое действие |
| FR-04 | Список машин и карточка | Только доступные, по 5, refresh/пустой список; карточка: номер/модель/статус/место с датой/топливо/одо/ключи/известные замечания |
| FR-05 | Неизвестные сведения и предыдущий осмотр | «Не указано» вместо выдуманных данных; без места/ключей выдача недоступна; previous after-осмотр без ФИО/истории чужого водителя |
| FR-06 | Намерение взять машину | Просмотр/первая кнопка не создают trip; подтверждение создаёт hold на 15 минут |
| FR-07 | Конкуренция | Одной машиной и одним сотрудником занята максимум одна assignment: hold или trip; проигравшему понятный отказ |
| FR-08 | Math перед важными операциями | 1..9 + 1..9, 4 уникальных ответа, один верный; ошибочный/чужой/старый/истёкший proof не меняет машину; 3 ошибки обновляют пример |
| FR-09 | Правила | Сохранены actor, версия текста и время; без принятия start запрещён; второй пример на итоговом start того же оформления не нужен |
| FR-10 | Топливо и одометр | Только заданные уровни; целые неотрицательные км, before не меньше предыдущего, after не меньше before; ошибка и контакт администратора |
| FR-11 | Комплект фото | Ровно один снимок каждого из 8 заданных ракурсов; при 7/8 start/complete запрещены с перечислением недостающего |
| FR-12 | Ошибки фото | Видео/текст/документ/multi-image/дубликат события не увеличивают счётчик; один и тот же файл не занимает два ракурса |
| FR-13 | Замена и подтверждение | Выбранный ракурс заменяется, 7 остальных остаются; итог 8/8; подтверждение комплекта сбрасывается до повторного согласия |
| FR-14 | Новое замечание before | Категория/описание и до 3 дополнительных фото; hold отменён, осмотр/issue сохранены, машина заблокирована, уведомление поставлено |
| FR-15 | Итоговое начало | Сводка + attestation; только после успешного сохранения одна trip, время старта, 8 фото и статус active |
| FR-16 | Отмена/TTL hold | Явная отмена или 15 минут освобождают hold; старая кнопка не начинает trip; новая попытка требует новых фото |
| FR-17 | Проблема во время/после | Issue виден администратору, активная trip не закрывается, следующая выдача блокируется; не обвинять водителя автоматически |
| FR-18 | Начать возврат | Намерение и math → draft return; trip и время продолжаются, машину другому не выдают |
| FR-19 | Честная анкета возврата | Повреждение/грязь допускают complete с блокировкой; проблемы ключей/закрытия/допустимой парковки запрещают обычный complete и создают обращение |
| FR-20 | Фото и сводка after | Новые 8 фото тех же ракурсов, топливо/одо/точка/замечания/ключи; открытый issue не закрывается ответом «новых нет» |
| FR-21 | Отмена return | Trip возвращается active; старый draft cancelled; следующий return не наследует фото или точку |
| FR-22 | Два способа парковки | MAX geo требует подтверждения; ручная карта доступна сразу и работает без GPS; нет обязательного текстового адреса |
| FR-23 | Выбор точки и ошибки | Центр карты не считается выбором; можно передвинуть маркер/добавить ориентир; при ошибке выбранная точка остаётся для retry; при отказе обоих способов сохранён draft |
| FR-24 | Авторизация карты | Сервер проверяет подпись/initData/auth_date, владельца, draft и version; чужой/закрытый/старый return не меняется |
| FR-25 | Итоговый возврат | В одной операции trip.completed, after, snapshot места/топлива/одо, release assignment, outbox; ошибка оставляет trip незавершённой |
| FR-26 | История | Только свои trips, новые сверху по 5; фото/место/данные/решение issue; попытки hold отдельно, закрытое нельзя редактировать |
| FR-27 | Обзор администратора | Все машины/активные trips/история/сотрудники/issues; фильтры сотрудник/машина; before/after сравниваются по ракурсу |
| FR-28 | Блокировка машины | Причина, сводка и math; hold отменяется, active trip сохраняется; unblock запрещён при открытых blocking issues |
| FR-29 | Исправления и решения | Описание/ключи с подтверждением; snapshot свободной машины с причиной и audit; активной — отдельное уточнение; исходные осмотры не меняются |
| FR-30 | Доступ сотрудников | Добавление по MAX ID/ФИО и изменение права с подтверждением/math; admin роль через bootstrap; история не удаляется |
| FR-31 | Аварийное закрытие | Admin, причина, сводка, math; closed_by_admin и missing_data; без выдуманных данных; машина needs_review; водитель уведомлён |
| FR-32 | Разбор замечаний | in_progress/resolved/known_nonblocking; последние два с комментарием/автором/временем; первоначальное сообщение сохраняется |
| FR-33 | Уведомления | Начало/возврат/issue/запрет/admin close только после commit; ошибка доставки не откатывает домен; повторная доставка отслеживается |
| FR-34 | Повтор команды/перезапуск | Одна бизнес-операция при duplicate/timeout; ранее сохранённые шаги доступны после restart; данные другого пользователя не раскрываются |
| FR-35 | Честность интерфейса | Последняя парковка с датой, не live GPS; math не проверяет трезвость/личность; распознавание повреждений и замки не заявляются |
| FR-36 | Реальные клиенты MAX | Меню, callbacks, фотографии, история и ручная карта проходят на мобильном и web-клиенте; различия geo не блокируют возврат |

## 3. Нефункциональные требования

| ID | Условие и измеримый результат |
|---|---|
| NFR-01 | 20 одновременных claims одной машины → один hold; один actor на 20 машин → один hold. Повторить на PostgreSQL минимум 10 серий; ноль двойных assignments |
| NFR-02 | Lost response после commit, duplicate event, повтор start/complete → тот же результат и один доменный эффект/outbox; different body с тем же key → 409 |
| NFR-03 | Restart Go/Python/worker на 4/8 фото, в return и после commit → подтверждённые данные сохранены, leases восстанавливаются, поездка не теряется |
| NFR-04 | БД/S3 недоступны: нет ложного успеха/засчитанного несохранённого фото; после восстановления можно продолжить |
| NFR-05 | Подмена ID, role, callback, initData, service secret, чужого asset/cursor → отказ без раскрытия данных; production не запускается с mock auth |
| NFR-06 | Реальные токены/PII/фото/DSN/initData/подписанные URL отсутствуют в Git, frontend bundle, логах и отчётах; приватный bucket, SQL/API не открыты наружу |
| NFR-07 | JPEG/PNG/WebP до 10 MiB и 25 MP; неверная сигнатура/большой файл/9-й слот отклоняются. Граничные значения тестируются; ограничение согласовано в S-02 |
| NFR-08 | На описанном стенде 50 concurrent users, 20 JSON API rps 10 мин: p95 ≤ 500 мс без времени внешних MAX/S3, unexpected 5xx < 1%. Отдельно 10 загрузок по 5 MiB без ошибок целостности |
| NFR-09 | Чистый checkout + локальные секреты → Docker full up; миграции до readiness, volumes переживают restart; никакой зависимости от локально установленного Go/Python |
| NFR-10 | Backup БД+S3 восстанавливается на чистые volumes; сходятся counts/FK/контрольные hash файлов; старая среда не повреждена |
| NFR-11 | Сервер UTC, UI часовой пояс компании; TTL на границах 14:59/15:00, challenge 4:59/5:00 и auth_date проверены с управляемыми часами |
| NFR-12 | Completed inspection неизменяем, административные действия имеют audit/причину; ошибка отправки MAX не меняет итог поездки |

Нагрузка — целевой критерий, не уже доказанная характеристика. Сильное различие ресурсов стенда фиксируется в отчёте. Требования безопасности и целостности нельзя компенсировать хорошим средним временем ответа.

## 5. Практический план QA

1. **QA-01:** составить cases и traceability. Минимальный формат кейса: ID; FR/AC; режим; предусловия/seed; шаги; ожидаемые данные/сообщения; приоритет; evidence.
2. **QA-02:** по мере появления функций проверять отдельно backend-mock и Python-real. Для Go — сообщения/маршруты, для Python — инварианты/API/БД/S3. Результаты не смешивать.
3. **QA-03:** подготовить финальный smoke/регрессию, устройства и fault-сценарии.
4. **INT-04…06:** реальный MAX, full stack, нагрузка/restart/restore, отчёт по всем требованиям.

Автоматизировать преимущественно API/транзакционные/контрактные тесты и проверку карты. Реальные разрешения геолокации, открытие mini-app и поведение MAX на телефоне проверить вручную: минимум один актуальный мобильный клиент и web. При наличии Android и iOS проверить оба; если один недоступен, явно записать непроверенный клиент.

Fixtures: разрешённый/неизвестный/blocked employee, admin с can_start_trip=false; free/holding/active/blocked машина; 8 разных синтетических фото, один дубль, неверный MIME, oversize; завершённая чужая trip. Изолировать данные каждого теста и не гонять destructive reset на демонстрационном сервере.

Пример кейса: TC-CLAIM-01 → FR-07/AC-03/NFR-01; два разных actor и одна свободная машина; синхронный POST checkout.create; ожидание — один success и один VEHICLE_UNAVAILABLE, одна assignment, второй actor без hold. Evidence: request_id, обезличенный query/result, code SHA.

## 6. Дефект, приёмка и короткая демонстрация

Дефект: заголовок; FR/AC; commit/contract/migration; режим/клиент; точные шаги; expected/actual; серьёзность; безопасное evidence. Critical: утечка, двойная выдача, потеря данных; high: основной start/return/map неработоспособен; medium/low — остальные по влиянию.

Приёмка P0: все AC и применимые FR/NFR проверены на соответствующем реальном контуре; нет critical/high; ошибки исправлены и перепроверены; Docker cold start/restart/restore выполнены; mock отключён. Любое исключение явно записано с причиной/риском и решением владельца. Пропущенная проверка не PASS.

Smoke 10–15 минут: unknown login → employee → выбрать и оформить машину с 8 фото → начать → админ видит active → отметить проблему → вернуть с 8 фото и ручной точкой без GPS → машина blocked → админ разбирает issue → проверить историю/фото/чужой доступ. Повторы и аварийное закрытие — отдельные короткие кейсы регрессии.

Вести результаты в [progress/QA.md](progress/QA.md); тест-кейсы и отчёт можно хранить в двух файлах tests/cases/P0.md и tests/acceptance/REPORT.md после их создания. Десять отдельных документов QA не нужны.

За пределами P0: будущее бронирование, оплата, замки, трекинг, AI-распознавание повреждений, multi-company, геокодинг адреса, экспорт. Их отсутствие не дефект P0.
